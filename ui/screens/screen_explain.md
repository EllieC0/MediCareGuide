# overall
All three screens share a common pattern: they use `st.session_state` to track
  user progress and call functions from `ui/components.py` for reusable elements
  like the language selector and chat interface.

  1. `welcome.py` — The Entry Point
  This is the first thing a user sees. Its job is to provide context and allow
  the user to ask general questions before starting the intake process.

   * `render_welcome()`: 
       * Displays a high-contrast Hero Banner with a large "Get Started" button.
       * Injects JavaScript to style the Streamlit buttons specifically for elderly users (larger fonts, taller targets).
       * Includes a RAG-grounded Chat: Uses `ask_welcome()` to query the Medicare & You 2026 handbook via `core/rag.py`.
       * Provides Accessibility Toggles: Allows users to turn on voice synthesis (TTS) and switch between "Fast" and "Private" inference modes.

  2. `intake.py` — The Guided Wizard
  This is a 5-step form designed to be non-intimidating. It collects the minimum data needed to find the right Medicare plans.

   * Step Logic: Each step (`render_step0_zip` through `render_step4_prefs`) uses large buttons or checkboxes.
   * Inline Explanations: Every step has an "Explain" button. When clicked, it renders a pre-written HTML table or card (like `_EXPLAIN_TRACK`) directly below the buttons to help the user choose without leaving the page.
   * Safe Q&A: A chat box is always available at the bottom of the intake steps. It allows users to ask questions like "What is an HMO?" while they are filling out the form.
   * State Management: It calls `_save_session_to_disk()` on every render to ensure that if the user refreshes their browser, they don't lose their place in the wizard.

  3. select.py — Recommendations & Analysis
  This is the most complex screen. It takes the user's profile and shows them actual plan data.

   * `trigger_select_mode()`: The "brain" function that transitions from the wizard to results. It filters the plans, sorts them based on user priorities, and asks Gemma 4 to analyze the top 5 options.
   * Two Tabs:
       * 📋 Recommendations: Shows the "Top 5" plans as foldable cards. Each card includes a "Why it fits you" section generated by the AI.
       * 🔀 Explore All Plans: A full, searchable table of every matching plan in the user's area with custom sorting controls (e.g., "Lowest Premium", "Star Rating").
   * Summary Export: Includes `_generate_summary_html()`, which builds a printable, self-contained HTML file that the user can download and take to their doctor or family.
   * Follow-up Chat: A specific chat handler (`handle_select_turn`) that stays focused on the plans currently being displayed.

  How they connect:
  The "glue" is in `main.py`, which acts as a router:

   1. `_screen = st.session_state.screen`
   2. `if   _screen == "WELCOME": render_welcome()`
   3. `elif _screen == "INTAKE":  render_intake()`
   4. `elif _screen == "SELECT":  render_select()`
  When a user clicks "Continue" in the wizard, `intake.py` increments
  `st.session_state.intake_step`. When it reaches 5, it calls
  `trigger_select_mode()`, which switches the screen to SELECT.

## welcome

In `ui/screens/welcome.py`, the `render_welcome()` function is the layout engine for the home page. It balances standard Streamlit widgets with custom HTML to create an interface that feels more like a dedicated web application than a data script.

Here is the breakdown of its functions and visual components:

  1. Header Functions (Language & Settings)
   * `render_language_selector("welcome")`: Calls a shared component to display the "EN | 中文 | ES" pill buttons.
   * Visual Component: Uses `st.columns` to push the selector to the top-right of the screen for easy access.

  2. The Hero Block (Visual & Interactive)
  This is the most customized part of the UI.
   * Custom HTML/CSS: Renders a `.hero-banner` div containing the badge, title, and tagline with a gradient background (defined in `style.css`).
   * `st.button("cta_button")`: A large "secondary" type button. 
   * Visual Component (`st.container`): Both the HTML banner and the button are wrapped in a single container. This allows the CSS to remove the "gap" between them, making the button look like it’s part of the banner's visual block.
   * The "Styling" Script (`st.html`): Injects a small snippet of JavaScript that finds the CTA button in the browser's DOM and forces it to be 80px tall with a 1.8rem font size. This ensures the primary action is impossible for an elderly user to miss.

  3. The Conversational Component
   * `render_chat_history()`: Iterates through `st.session_state.chat_history` and renders messages using Streamlit's native `st.chat_message` containers.
   * Visual Component (Inline Form): Instead of the standard bottom-pinned
     `st.chat_input`, it uses `st.form`. 
       * Why? The standard chat input is fixed at the bottom of the viewport. By using a form, the chat input stays inline with the page flow, allowing other information (like "How it Works") to scroll below it.
   * `render_voice_input("welcome_mic")`: Adds the microphone icon. If transcription is successful, it automatically triggers the form submission.

  4. Educational & Functional Footer
   * "How it Works" Grid: Uses `st.columns(3)` to render three "Step Cards" (1, 2, 3). These are pure HTML blocks that explain the project's logic (Learn → Answer → Choose).
   * Inference Toggle: A functional row at the bottom that uses `st.button` and `st.info` to let the user switch between Fast Mode (Cloud) and Private Mode (Local).
   * Audio Toggle: A final `st.button` that turns on the read-aloud (TTS) feature. It changes its label dynamically based on `st.session_state.audio_enabled`.

  5. Deferred Audio Processing
   * Logic Block: You’ll notice a check for `_pending_tts_text`. 
   * Visual Component: This doesn't render a visible element, but it triggers `st.audio`. It’s placed here so that the text response appears first in the chat history, and then the audio starts playing on the subsequent "rerun," preventing the UI from freezing while the AI voice is being generated.

## intake

The `ui/screens/intake.py` module handles the data collection phase using a 5-step wizard. It is designed to be non-intimidating and highly accessible.

### 1. The Main Router: `render_intake()`
This is the parent function responsible for rendering the overall layout and orchestrating the steps.
*   **State Management:** Calls `_save_session_to_disk()` on every render to ensure progress is saved.
*   **Progress Indicator:** Uses `st.progress()` to visually show the user's progress through the 5 steps.
*   **Step Routing:** Uses `st.session_state.intake_step` to determine which step function (`render_step0` to `render_step4`) to display.
*   **Contextual Chat:** Renders an inline chat form at the bottom so users can ask questions without leaving the wizard.

### 2. Step Functions (`render_step0` to `render_step4`)
Each function collects a specific piece of the user's profile:
*   **Step 0 (ZIP):** Collects and validates the 5-digit ZIP code.
*   **Step 1 (Track):** Three large buttons for Medicare Advantage, Part D, or Medigap.
*   **Step 2 (SNP):** Checkboxes for Dual Eligible, Chronic Condition, and Extra Help (LIS).
*   **Step 3 (Budget):** A dynamic UI with a slider for monthly premium limits.
*   **Step 4 (Preferences):** Checkboxes for prescriptions, doctor networks, and dental benefits.

### 3. The Explanation System
To help users understand complex terms, the module uses:
*   **HTML Constants:** Pre-styled HTML tables/cards like `_EXPLAIN_TRACK` and `_EXPLAIN_SNP`.
*   **Inline Rendering:** Clicking an "Explain" button triggers `_render_inline_explain()`, which injects the helpful content directly below the action buttons.

## select

The `ui/screens/select.py` module is the "brain" of the application. It gathers all the intake results, filters the plan database, and runs the Gemma 4 AI model for personalized analysis.

### 1. Data Gathering & AI Execution: `trigger_select_mode()`
This function is called once the intake wizard is complete (`step >= 5`). It performs the following:
*   **Profile Retrieval:** Pulls the collected data from `st.session_state.session.state["profile"]`.
*   **Filtering & Sorting:** Calls `lookup.get_plans_filtered()` and `sort_plans()` to identify the top matching plans based on the user's budget and preferences.
*   **AI Prompting:** Uses `build_prompt_select_mode()` to construct a detailed prompt for Gemma 4, including the user's profile and the top 5 plans.
*   **Model Call:** Executes `call_ollama()` to generate a personalized "Why it fits you" analysis for each recommendation.

### 2. Result Visualization
*   **Recommendations Tab:** Shows the top 5 plans as expandable cards. Each card includes the AI-generated justification.
*   **Explore All Tab:** Provides a comprehensive, sortable table of every matching plan in the user's ZIP code.
*   **Exporting:** Includes `_generate_summary_html()`, which creates a downloadable PDF-style summary for the user to keep.


## intake

 Based on the implementation in `ui/screens/intake.py`, here is a breakdown of the function and visual components that make up the Intake screen. It follows a modular "wizard" pattern rendering different UI components based on the user's current step.
1. The Main Router: `render_intake()`
  This is the parent function responsible for rendering the overall layout
  of the screen and orchestrating which step to show.

   * State Management: It begins by `calling _save_session_to_disk()` to ensure progress is saved. If a user refreshes the page, they won't lose their place.
   * Header Component: Renders the main title and places the `render_language_selector` in the top-right corner using column layouts.
   * Progress Component: Uses `st.progress()` to visually indicate how far the user is in the 5-step process.
   * Step Routing: A simple `if/elif` block checks `st.session_state.intake_step` (0 through 4) and calls the corresponding `render_stepX()` function. If the step reaches 5, it triggers the transition to the Select screen via `trigger_select_mode()`.
   * Persistent Chat UI: Below the active step, it renders a contextual chat box using st.form (to keep it inline rather than pinned to the bottom). This allows users to ask questions like "What is an HMO?" while actively filling out the form. It also includes voice input (`render_voice_input`).
   * Navigation: A "Back" (←) button at the very bottom allows users to return to the previous step or back to the Welcome screen.

2. The Step Functions (`render_step0` to `render_step4`)
  Each step function is responsible for a single piece of the data collection process. They all share a similar structural pattern:
   1. Visual Prompts: `st.subheader` and `st.caption` for clear, large instructions.
   2. Input Widgets: Large targets (text inputs, buttons, checkboxes, sliders) for data entry.
   3. Action Row: "Continue" or "Skip" buttons, alongside an "Explain" button.
   4. State Updates: When an action button is clicked, it updates the backend session state (set_intake_field) and reruns the app to advance to the next step.

  Here is what each step collects:
   * `render_step0_zip()` (Location):
       * Visual: Uses `st.text_input` restricted to 5 characters.
       * Logic: Validates that the input is exactly 5 digits. On success, it looks up the county/state to provide a friendly confirmation message (e.g., "Found plans in King, WA") before advancing.
   * `render_step1_track()` (Coverage Type):
       * Visual: Uses a 3-column layout (`st.columns(3)`) offering large primary buttons for Medicare Advantage, Part D Only, or Medigap.
   * `render_step2_snp()` (Special Needs):
       * Visual: Uses st.checkbox for Dual Eligible (D-SNP), Chronic Condition (C-SNP), and Low Income Subsidy (LIS).
       * Logic: Collects multiple flags in an array. Offers a "None of these" button to easily skip.
   * `render_step3_budget()` (Monthly Cost):
       * Visual: A dynamic UI. If the user checks the "I don't have a strict limit" box, the budget slider is hidden. Otherwise, it shows an st.slider capped at $500/month.
   * `render_step4_prefs()` (Plan Preferences):
       * Visual: Checkboxes for specific needs (regular prescriptions, keeping doctors, dental/vision, preferring PPO).
       * Action: The primary button here changes from "Continue" to "Find my plans", indicating the end of the wizard.

3. The Explanation System
  Because Medicare is confusing, the intake form includes an inline
  explanation system so users don't have to leave the page to look up terms.

   * HTML Constants: At the top of the file, there are several large, styled
     HTML string constants (`_EXPLAIN_TRACK`, `_EXPLAIN_SNP`, `_EXPLAIN_BUDGET`, `_EXPLAIN_PREFS`). These contain visually distinct tables and colored callout boxes.
   * `_render_inline_explain(step)`: This helper function is called at the end of every step function. 
   * Logic: When a user clicks an "Explain" button (e.g., "Explain the difference"), it sets the active `explain_step` and stores the relevant HTML constant in `explain_text`. `_render_inline_explain` detects this state and renders the HTML directly below the buttons with a distinct blue border, providing immediate context.

4. The Medigap Exception: `render_medigap_referral()`
  If a user selects "Original Medicare + Medigap" in Step 1, the standard
  intake flow stops. 
   * Why? The project's data (CMS Landscape) only covers Advantage and Part D plans, not private Medigap policies.
   * Visual: Replaces the intake form with a specific landing page containing a warning, an external link to Medicare.gov, and a focused chat interface so the user can still ask general Medigap questions. It includes a "Start Over" button to reset the session.
